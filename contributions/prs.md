### [#472](https://github.com/braidpool/braidpool/pull/472) — fix(stratum): derive extranonce1 from atomic connection_id counter
**Merged:** 2026-06-05 | **Closes:** issue #461

#### Problem
Multiple miners connecting to the same node received identical `extranonce1` values. Root cause: `extranonce1` and `connection_id` were generated by two independent `rand::thread_rng()` calls, neither derived from the other. Random assignment collides with near-certainty around 65k concurrent miners (birthday problem on a 32-bit space). Two `FIXME` comments in `DownstreamClient::default()` pointed at exactly this gap.

#### Approach
Replaced both RNG calls with a single monotonically increasing `AtomicU32` counter. `extranonce1` is now derived directly from `connection_id` via `to_be_bytes()` — miner 0 gets `00000000`, miner 1 gets `00000001`, guaranteed unique, non-overlapping nonce partitions. Removed the now-unused `rand::RngCore` import. Added a test asserting monotone IDs, unique extranonces, correct size, and correct big-endian encoding.

#### Design note
`Ordering::SeqCst` on the counter could be relaxed to `Ordering::Relaxed` in a follow-up — the counter only needs to produce unique values, not coordinate memory visibility with anything else.

#### Review
- **mcelrath** (Code ACK): "Good catch, and good solution."

### [#475](https://github.com/braidpool/braidpool/pull/475) — feat: extend extranonce1 and extranonce2 to 8 bytes each
**Merged:** 2026-06-17

#### Problem
Both extranonce fields were 4 bytes (`u32`). Modern ASICs exhaust a 4-byte extranonce2 (~4 billion combinations) in milliseconds, forcing miners to request new jobs far more often than necessary.

#### Approach
Extended both fields from `u32` to `u64` — 16 bytes of total extranonce space. The change propagates through stratum parsing, uncommitted metadata struct, consensus encoding/decoding, DB layer, and test utilities. `extranonce1` continues to be derived from the atomic `connection_id` (zero-padded into 8 bytes via `(connection_id as u64).to_be_bytes()`), preserving the uniqueness guarantee from #472.

The `submit_work_version_rolling` test was coupled to a specific CPUNet block vector. With a different coinbase size the old nonce no longer produces a valid hash — the assertion was updated to verify that version rolling parsing completed without error, which is what the test is actually checking.

#### Review
- **zaidmstrr**: Raised inconsistencies in documentation and a medium-level issue around extranonce sizing; both addressed across two pushes. Code ACK on final commit.
- **mcelrath**: Commented (no blocking issues).

### [#477](https://github.com/braidpool/braidpool/pull/477) — fix(tests): replace hardcoded stratum ports with OS-assigned port 0
**Merged:** 2026-06-11

#### Problem
All five stratum tests bound fixed ports (3353, 3356, 3357, 3358, 5050). If a previous test left a server running or two tests raced to bind the same port, the test failed with `AddrInUse` — a misleading error that looked like a code bug rather than a port conflict. This was first noticed while reviewing PRs #309 and #474.

#### Approach
Added an optional oneshot channel parameter to `run_stratum_service`. After binding, the server sends its actual address back through the channel. Tests use port 0 so the OS assigns a free port, then await the receiver before connecting — no sleep, no race window, no hardcoded ports.

This pattern was already in use in `rpc_server.rs` via `server.local_addr()`, so the approach is consistent with the rest of the codebase. Production call in `main.rs` passes `None`, zero impact outside tests.

#### Review
- **zaidmstrr** (Concept ACK → Code ACK): "The problem seems to exist." Suggested a follow-up refactor to move `TcpListener::bind` to the caller entirely — this became #479.

### [#479](https://github.com/braidpool/braidpool/pull/479) — refactor(stratum): move TcpListener binding to caller
**Merged:** 2026-07-06

#### Problem
`run_stratum_service` was doing two things: binding a port and running the server loop. Tests had no way to discover the actual bound port without the oneshot channel added in #477. The approach worked but added API surface (the `Option<Sender>`) that existed purely for tests.

#### Approach
Moved binding entirely to the caller. `run_stratum_service` now accepts a ready `TcpListener` as its first argument. Callers bind the socket themselves — port 0 for tests, the configured port for production — and pass it in. The function calls `listener.local_addr()` for logging and proceeds directly to the accept loop.

Tests now bind their own listener before spawning, read the port directly from `local_addr()` — no channel, no sleep, no race window. Removes the `port` field from `StratumServerConfig` (no longer used inside the server). Consistent with `rpc_server.rs` which already followed this pattern. Removes the oneshot channel from #477.

#### Review
- **Sansh2356** (t-ACK): Suggested also removing `port` from `StratumConfig` — implemented.
- **zaidmstrr** (Approach ACK → Code ACK): Left nits on logging and config cleanup; all resolved before merge.

### [#482](https://github.com/braidpool/braidpool/pull/482) — fix(tests): replace hardcoded RPC server ports with OS-assigned port 0
**Merged:** 2026-07-03

#### Problem
RPC server tests were binding to hardcoded ports (9001–9101, 8889, 9000, and others). Same failure mode as #477: parallel test runs or TIME_WAIT sockets caused `AddrInUse` failures with misleading error messages. 16 tests used `run_rpc_server` with fixed ports; 4 used `Server::builder().build()` directly. One test (`test_get_peer_info_rpc`) had two server instances inside a single function, each on a different hardcoded port. #### Approach
Same fix as #477, applied to the RPC layer. All 16 `run_rpc_server` tests switch to `"127.0.0.1:0"` and capture the returned `SocketAddr`. All 4 `Server::builder()` tests call `server.local_addr()` after build. Removed 6 blind sleep calls.

### [#498](https://github.com/braidpool/braidpool/pull/498) — test(stratum): assert BIP310 mask negotiation in submit_work_version_rolling
**Merged:** 2026-07-12

#### Problem
`submit_work_version_rolling` built a `configure_response` and immediately discarded it — the BIP310 mask negotiation (ffffffff & 0x1FFFE000 = 1fffe000) ran completely unverified. The test exercised the submit path but left the configure phase untested, so a regression in mask negotiation would go undetected.

Two assertions, one for the protocol response and one for the internal state that drives subsequent validation.

### [#492](https://github.com/braidpool/braidpool/pull/492) — refactor(stratum): replace per-miner MiningJobMap with GlobalJobStore
**Status:** Draft (awaiting rebase after #509 merge) | **Supersedes:** #484

#### Problem
Every miner connection had its own `MiningJobMap`. The notify loop cloned the full block template (~100–500 KB) once per miner on each new bead:

```rust
for (peer, map) in job_map_arc.iter() {
    let template_for_job = template.clone(); // ~100–500 KB per miner
    map.insert_mining_job(template_id, job_details).await;
}
```

At 10,000 miners that's 5 GB allocated per new template. At 150ms bead rates the node OOM-crashes within hours.

The earlier fix attempt (#484) added per-miner capacity capping with monotonic-ID eviction. This was closed after mcelrath identified that evicting by `template_id` silently invalidated other `job_id`s pointing at the same template — the correctness bug required replacing the per-miner architecture entirely.

#### Approach
Single shared `GlobalJobStore` across all connections, via `Arc<Mutex<GlobalJobStore>>`. `JobDetails` is `Arc`-wrapped — one allocation shared by all miners, zero template clones on notify. The notify loop builds the job once and sends N pointer copies.

Key design decisions:
- **`entry().or_insert()`**: If two job_ids point at the same `template_id`, the existing `Arc` is reused — no duplicate allocation.
- **`latest_job_id_for()`**: Resend path for newly-connecting miners reuses the existing `job_id` for the current template instead of minting a new one. Minting per-connection advances `next_job_id` and eventually evicts the id every already-connected miner is submitting against. Reuse makes the notify loop the only job_id source in steady state.
- **Eviction correctness**: Template data freed only once no remaining `job_id` references it — fixes the #484 bug where evicting by `template_id` invalidated other job_ids pointing at the same template.
- **Capacity**: `GLOBAL_JOB_STORE_CAPACITY = 20` (~3s retention at bead rate). Original revision used 5 (~750ms, half of the old per-miner limit). Raised to 20 because the per-miner cap was constrained by per-connection memory pressure; with one shared store that no longer applies.

Memory result: ~5 GB → ~500 KB at 10k connections.

#### Rebase (post-#509 merge)
#509 introduced `TemplateId::Upstream(String)` (non-Copy), `is_upstream_job` on `JobDetails`, and audit-mode params in `handle_submit`. The rebase required:
- Fixing all Copy-assumption patterns (`|&tid|` → `|tid| tid == &x`, `entry(id)` → `entry(id.clone())`, `Some(*tid)` → `Some(tid.clone())`)
- `get_by_string_job_id` as a thin wrapper over `jobs.get(&TemplateId::Upstream(s))`
- `clear_upstream_jobs()` rewritten to `retain` dropping `TemplateId::Upstream` variants
- Keeping HEAD's full audit routing in `handle_submit` (string-first → numeric fallback → `is_upstream_job` branch)
- `latest_job_id_for` signature changed to `&TemplateId` (non-Copy-safe)
- All second-commit tests updated for the new API (`TemplateId::Braidpool(n)` instead of raw integers)

#### Review
- **zaidmstrr** (Approach ACK): "Great refactor and optimization. Dependent on #509 — rebase required after that merges."
- **copilot**: Automated review on three changed files.

### [#503](https://github.com/braidpool/braidpool/pull/503) — feat(stratum): add per-miner share counters (accepted/stale/invalid)
**Status:** Open

#### Problem
`handle_submit` decides the outcome of every share — accepted, stale, invalid — then discards that decision entirely. An operator cannot answer basic operational questions: which miners are slow? which are sending garbage? what's the pool's error rate? This also blocks the `getminer` RPC (#298) and dashboard miner stats (#501), both of which need this data to exist before they can expose it.

#### Approach
`DownstreamClient` gains a `ShareCounters { accepted, stale, invalid: u64 }` field, bumped at semantic decision points in `handle_submit`:

- `invalid`: malformed params, bad hex, mask violation, PoW below target
- `stale`: well-formed share for a job no longer in the store (timing failure, not correctness)
- `accepted`: share passed all validation including PoW

Counters logged at disconnect. Five unit tests cover each counter path independently.

**Why explicit bump sites, not a return-type wrapper**: Below-target shares return `Ok(json!(false))` per Stratum convention — the network response succeeded, the share was rejected. A wrapper classifying `Ok` as accepted would count every failed PoW as accepted, which is the most common rejection in real mining. Bumps are at explicit decision points for this reason; the fourth test pins the below-target case permanently.

**Post-#509 rebase note**: Audit-mode submissions return early via `validate_and_forward_upstream_share` before any counter, so these counters cover the Braidpool submit path only. Audit mode has its own accounting via `AuditDAG` and `MinerStatsView`, though that view tracks valid beads only and doesn't expose an error rate. The authorization gate now sits upstream of every bump, so an unauthorized `mining.submit` is counted nowhere — left that way deliberately (protocol-state violation, not a share-quality signal).

#### Review
- **copilot**: Automated review.

### [#508](https://github.com/braidpool/braidpool/pull/508) — fix(tests): eliminate shared SQLite state causing parallel test races
**Status:** Open | **Fixes:** #504

#### Problem
`server_start_test` and other stratum tests fail intermittently on CI. All stratum tests called `DBHandler::new()` which writes to `~/.braidpool/braidpool.db`. With parallel test execution, two tests race at schema creation — one errors with `table Bead already exists` or `database is locked`.

#### Approach
Three changes:
1. **`schema.sql`**: Added `IF NOT EXISTS` on all `CREATE TABLE`, `CREATE INDEX`, `CREATE VIEW`. Eliminates the already-exists race for any file-based test.
2. **`DBHandler::new_in_memory()`**: New `#[cfg(test)]` constructor using `sqlite::memory:`. Critical subtlety: `sqlite::memory:` gives each connection its own private database — requires `max_connections(1)` so all queries share one connection and therefore one schema. Schema embedded via `include_str!`, no file path dependency.
3. **`stratum.rs`**: All six `DBHandler::new()` call sites in tests switched to `new_in_memory()`. Each test gets a private isolated database.

#### Review
- **Sansh2356**: DRY feedback — removed `test_db_initializer()` helper.
- **copilot**: Suggested `max_connections(1)` and `db_connection_pool.execute(SCHEMA)`, both applied.

### [#484](https://github.com/braidpool/braidpool/pull/484) — fix(stratum): cap MiningJobMap per miner
**Status:** Closed, superseded by #492

#### Problem
`MiningJobMap` had no capacity bound. At bead rate, old jobs accumulated indefinitely per miner.

#### Approach
Added `capacity: usize` to `MiningJobMap` with monotonic-ID eviction — when at capacity, the oldest `job_id` is removed and its template freed.

#### Why it was closed
mcelrath identified that evicting by `template_id` silently invalidated other `job_id`s pointing at the same template via the resend path. The correctness bug meant the right fix was to replace the per-miner architecture entirely, not just add a cap. → #492.

### `fix/stratum-fail-fast-ntime-nonce` — fix(stratum): fail fast on malformed ntime/nonce

#### Problem
`ntime` and `nonce` are extracted at lines 615/624 but parsed ~180 lines later, after job lookup (mutex acquisition), coinbase hex decode, `Transaction::consensus_decode`, merkle branch decoding, and `calculate_merkle_root` (multiple SHA256 rounds). Neither parse depends on any of that work. A submission with unparseable ntime pays the full CPU cost before being rejected. With no submit rate limiting, this is a CPU amplifier per bad request.

Also: the extranonce2 length-mismatch error message reported `self.extranonce2_len` instead of `self.miner_extranonce2_size`. Both fields are always assigned together and currently equal, so the message was correct by coincidence rather than construction.

**Investigation note**: The original item was "no extranonce2 length validation" — that gap was already closed by #509 (complete check at 577–593 with separate hex-validity check). The reordering was the real finding.

#### Approach
Three changes:
1. Move both parse blocks to immediately after the audit-mode early return (~line 698), before any coinbase work.
2. Fix the extranonce2 error message to read `self.miner_extranonce2_size`.
3. Two new tests:
   - `non_hex_ntime_returns_err_before_coinbase_work` — non-hex ntime returns `Err(InvalidMethodParams)`.
   - `unpadded_nonce_is_accepted_by_parser` — nonce `"3"` (formatted with `{:x}` instead of `{:08x}`) returns `Ok(false)` (PoW miss), not `Err`. Pins the reasoning for not adding strict 8-char length validation: `from_str_radix` handles unpadded values correctly, and rejecting them would reject valid work.

**Deliberately not done**: strict 8-char length validation. A miner using `{:x}` sends `"3"` for nonce 3; `from_str_radix` parses it correctly. Length validation would reject work that currently succeeds.

**Follow-up needed**: Both parse-failure paths should bump `invalid` (from #503) once that PR merges. Currently every other validation failure in `handle_submit` bumps the counter; these two were missed.
